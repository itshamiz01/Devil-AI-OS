### 1.1 Duplicate-purpose / orphan / unused — verdicts

- **Orphan tables: none.** Every one of the 171 model classes is referenced outside `database/models/` (app code
  and/or repositories). No table is defined-but-never-touched.
- **Businesses: exactly one identity table** — `businesses` (P-06). `business_portfolios` is a portfolio container
  and `portfolio_business_memberships` a join table; neither duplicates business identity. PASS.
- **Approvals: exactly one store** — `approvals` (P-01, `models/core.py`). P-12 deliberately did **not** build an
  `approval_requests` table (verified: no such table in metadata); `operations_approval_links` is a link table
  (workflow/task ↔ `approvals.id` FK) and `business_*`/`security_*` `approval_id` columns are references, not stores. PASS.
- **Agents: exactly one identity table** — `agents` (P-01 core models, VARCHAR(64) PK); P-04/P-06/P-12/P-13 add
  satellite/assignment tables FK'd (or, in places, not FK'd — §2) to it. PASS on identity, see D-defects on assignments.
- **Near-duplicates by design (flagged, not defects per se):** four assignment tables and three workflow stacks —
  see Integration Matrix D1/D2. `cash_balances` is a derived cache of ledger state (P-07 owns both, so no cross-module
  conflict). `survival_forecasts.p07_forecast_id` references P-07 `financial_forecasts` without an FK (§2).

## 2. FK-less reference columns (116)

Raw count from metadata: **116 columns named `*_id` with no `ForeignKey`** (and not a PK). They fall into three classes:

**(a) Polymorphic principal/actor references — by design (≈45).** Columns such as `*_by_id`, `requester_id`,
`creator_id`, `principal_id`, `actor_id`, `approver_id`, `granted_by_id`, `changed_by_id`, `holder_id`, `owner_id`
are `VARCHAR(200)` free principal identifiers (owner is the literal `"owner"`, agents/services use typed IDs) and
cannot FK to a single table. Includes `permissions.principal_id`, `app_sessions.principal_id`,
`approvals.requesting_principal_id/approver_id`, `audit_events.actor_id/target_id`, `tasks.creator_id`.

`security_broker_decisions`, `system_events`), `system_events.event_id/task_id`, `payment_events.external_event_id`,
`model_profiles.model_id` (a provider model name, not a row), `dashboard_notification_states.notification_id`.

## 4. Consistency checks (from code)

- **ID types — mixed widths, one type family.** All PKs are strings except 4 INTEGER PK tables. Distribution:
  `VARCHAR(36)` PK ×127 (UUID, P-06…P-13 era), `VARCHAR(64)` PK ×40 (P-01…P-05 era), `INTEGER` PK ×4.
  IDs are UUID strings generated by `new_uuid()` (`models/base.py`) — consistent in kind, **inconsistent in width**,
  and several FK-less reference columns declare a *different width than their target PK* (e.g.
  `business_agent_assignments.agent_id` VARCHAR(36) → `agents.id` VARCHAR(64); `new_venture_proposals.opportunity_id`
  VARCHAR(36) → `opportunities.id` VARCHAR(64); `memory_records.agent_id` VARCHAR(120)). SQLite ignores VARCHAR
  widths, so nothing fails today; on any stricter engine these are truncation/type hazards. → P14-DEF-D3.
  Business identifiers specifically: `businesses.id` is VARCHAR(36) and most FKs match, but four modules also carry
  free-text `business_ref` VARCHAR(200) (agents, assignments, execution, security broker) which can hold a business
  id, name, or external ref — no constraint ties it to `businesses.id`. → P14-DEF-D4.
- **Timestamps — the P-12 naive/aware defect class is mitigated in application code, not in schema.** All model
  `DateTime` columns split as: **320 columns `DateTime(timezone=False)` via `TimestampMixin`/plain `mapped_column`
  vs 64 columns explicitly `DateTime(timezone=True)`** (measured from metadata: `DATETIME_TZ {False: 320, True: 64}`).
  `models/base.py:21-23` `TimestampMixin` declares `created_at/updated_at` with **no `DateTime(timezone=True)`**,
  while `utcnow()` returns an aware UTC datetime. On SQLite, aware values round-trip back **naive** — which is
  exactly why P-12 carries defensive re-attachment shims (`operations/scheduling.py:27-36` — "SQLite round-trips
  strip tzinfo"; `operations/service.py:919-920,952-953,2454-2455,2529-2530,3075-3076`). Other modules comparing a
  DB-read timestamp against `utcnow()` without such a shim remain exposed. Additionally several temporal fields are
  stored as **strings** (`businesses.launched_at` VARCHAR(40), `memory_records.expires_at/verified_at` VARCHAR(40),
  financial `entry_date/period_start` VARCHAR(10) ISO dates — the latter are deliberate date-only fields).
  → P14-DEF-D2 (P1).
- **Currency — P-07 discipline verified, two float exceptions outside it.** Every P-07 amount is
  `amount_minor: BigInteger` + `currency: VARCHAR(8)` (`models/financial.py:156,190,207,228,250,269,296,373,463,488,521`
  and peers); P-08 money fields follow the same pattern (`estimated_cost_minor`, `amount_minor`, `budget_minor` +
  currency). **Float scan across ALL models: 12 FLOAT columns** — 10 are non-money (timeouts, durations, scores,
  metric values: `tasks.timeout_seconds`, `execution_runs.duration_ms`, `opportunity_scores.weighted_score`, …) and
  **exactly 2 are money-valued: `business_declarations.budget_cap_amount` FLOAT (`models/business.py:111`, with a
  separate `budget_currency`) and `research_briefs.budget_amount` FLOAT (`models/opportunities.py:29`)**. Both are
  pre-P-07 *declaration/estimate* caps, not ledger amounts — no float ever reaches the journal — but they are the
  only places a monetary value can accumulate binary-float error, and P-08/P-12 read declaration caps when gating.
  → P14-DEF-D1 (P2).
- **Business identifier consistency:** see ID bullet — canonical `businesses.id` (36-char UUID) everywhere in FK'd
  columns; inconsistency is confined to `business_ref` strings and FK-less refs.

## 6. Duplicate-record risks / unique constraints

| Entity | Protection found | Gap |
|---|---|---|
| Businesses | `businesses.slug` UNIQUE | `name` not unique — two businesses may share a name; slug is the only guard |
| Agents | No unique constraint on `agents` (name/role/template all repeatable — intentional, agents are instances) | Duplicate *creation* is guarded by `agent_creation_requests.idempotency_key` UNIQUE, not by the agent row |
| Tasks (P-01) | `tasks.idempotency_key` UNIQUE (nullable) | Callers that omit the key can duplicate tasks; same pattern in `agent_assignments`, `execution_requests` (UQ on the column), `autonomous_workflows` |
| Financial postings | `journal_entries.idempotency_key` UNIQUE — double-posting mechanically prevented; corrections reversal-only (`reversal_of_id` FK) | Source-document tables (`expense_records`, `spending_requests`, `task_cost_records`) have **no** unique natural key — a duplicated expense *record* is possible even though its journal posting is deduped |
| Memory entries | Exact-hash dedupe only — **verified**: `memory_records.content_hash` has **no unique constraint**; dedupe is application-level (`memory/ingestion.py:114-117` `by_content_hash` lookup before insert; `memory/records.py:30` hash of title+content). Near-duplicates (same content, different title; paraphrases) are not detected — consistent with the P-09 report | Race: two concurrent ingestions of identical content can both pass the lookup and insert |
| Approvals | No unique constraint (correct — approvals are per-request instances); single-use/replay protection is service-level (P-10) | — |
| Shared services | `shared_service_access` UQ(service_id, business_id) | — |
| Blueprints/templates | `business_blueprints` UQ(business_id, version); `security_policy_versions.version` UQ; `agent_capabilities.name`, `execution_tools.name` UQ | — |

## 7. Data-architecture defects

| ID | Sev | Defect | Minimal proposed repair (Stage B) |
|---|---|---|---|
| P14-DEF-D1 | P2 | Two float money columns outside the P-07 integer-minor discipline: `business_declarations.budget_cap_amount`, `research_briefs.budget_amount` | Add `*_minor BIGINT` + keep currency, backfill `round(amount*100)`, deprecate the floats in a new additive migration |
