## 2. Design decisions proposed for P-06 (owner can amend before build)

1. **Creation is workflows all the way down.** A template is a `WorkflowEngine` definition whose steps are P-05 execution requests (file writes, API reads/writes, code runs). No new execution path, no direct `requests`/`subprocess` call from a P-06 service. If a template step cannot be expressed as an existing execution tool, the template is rejected at validation — the gap is recorded, not worked around.
2. **A template is data, never code.** Templates are versioned JSON (steps, inputs schema, allowed tools, budget caps, platform gates) validated against the tool registry. An unregistered tool name, a step outside the template's declared tools, or a template edit after a unit pinned it is rejected. This is the same anti-smuggling rule P-01 enforced for tasks and P-04 for agent templates.
3. **Pre-declaration is a gate, not paperwork (Constitution rule).** Before any creation or launch step runs, the owner (or a launch record they approved) declares: success criteria, budget, duration, minimum test volume. The launch cannot start without it, and the gate judges the launch against the declaration — never against a checklist. The prompt pack's own exit line governs here: "A launch checklist completed ≠ a successful business."
4. **Platform gates are design, not patch.** This is the first phase that creates things in the real world (product, page, listing), so every external publish step passes a platform-gate check first: the platform's rules for AI/agent-created content, whether agent sign-in is even possible, and whether the action is reversible. Known gate, already proven: **KDP blocks AI-agent sign-in** (verified 8 Nov 2026 — Muse's browser got Amazon's 'Access restricted' page, and a user takeover in that browser failed the same way). So a KDP publish step can only ever produce a **prepared package + REQUIRES_HUMAN_ACTION**, never an attempted sign-in. The same pattern applies to every platform: publish steps default to DRAFT/prepared; a live publish needs a hash-bound owner approval AND a passing platform-gate check, and the gate result is recorded as evidence either way.
5. **Financial boundary stays shut.** No payment, purchase, charge, payout, or transfer path is built. Pricing is data (a price field on a product draft), not a transaction; an order is recorded only as an external reference + status, with no money fields — money movement and reconciliation are P-07. Any template step that would move money is rejected as out of scope. This is a testable gate assertion, not a comment.
6. **Business isolation is enforced, not assumed.** One managed workspace per unit; permissions and capability grants scoped per unit; a unit's agent cannot read another unit's data, files, or evidence without authorisation (SYSTEM_ARCHITECTURE component F rule). Cross-unit access is a named security test, and a violation is a persisted critical event.
7. **Deterministic-first, same as P-02/P-03/P-05.** The acceptance scenario must pass with no LLM, no live platform, and no browser engine installed, using fixture templates and fake transports — the machinery (template validation, workflow drive, approval gate, isolation, audit) is what the gate proves. A real platform call is then the same code path with a real transport, not a second implementation.
8. **No outreach, no auto-posting.** `external_communication` stays ungrantable, so acquisition plans are drafts (audience, channel, copy, budget as data). Anything that would send a message, post publicly, or contact a person goes through the platform gate + owner approval as a P-05 `api_write`/`browser` step — or is refused with `REQUIRES_HUMAN_ACTION`. P-06 builds no send path.
