## 2. Design decisions proposed for P-05 (owner can amend before build)

1. **Execution is handlers all the way down.** No `os.system`, no `subprocess`, no direct `requests`/`playwright` call from a service. Each capability maps to one registered handler with a Pydantic payload model: `exec.file_read`, `exec.file_write`, `exec.api_read`, `exec.api_write`, `exec.browser_navigate`, `exec.browser_extract`, `exec.external_send` (if the owner's P-05 prompt allows it — default: not built). The P-01 anti-smuggling rule applies unchanged: an unregistered tool name in a plan is rejected at validation.
2. **Sandbox by allowlist, not by trust.** File handlers operate only inside one owner-configured workspace root (no `..` escape, no absolute paths outside it, symlinks resolved and re-checked). API/browser handlers call only hosts on an owner-governed allowlist with per-host method and rate limits; credentials are never in payloads — they come from owner-configured, redacted secret references. Timeouts and size caps on every call; anything outside the allowlist fails closed with a recorded denial, never a bypass.
3. **Deterministic-first, same as P-02/P-03.** The acceptance scenario must pass with no LLM and no browser driver installed, using a fake transport and fixture files — the machinery (task submission, capability check, verification, audit) is what the gate proves. Real browser/API execution is then the same code path with a real transport, not a second implementation.
4. **Capability grants are the only door.** An agent may use an execution handler only if `CapabilityService.has_capability` says so for that agent, the grant is unexpired, and the P-01 permission mirror allows it. The P-02 planner must refuse to emit a plan step naming a tool the assigned agent does not hold — the plan fails at validation, not at runtime.
5. **Every external effect is an auditable artifact.** Each execution step persists: the exact request (method/URL/path, redacted), the result or failure, bytes/time/cost, the verification verdict, and the correlation ID linking mission → plan → task → agent → artifact. A step whose result cannot be verified is reported `unverified`, never silently "done".
6. **Financial boundary stays shut.** `financial_transaction_request` records requests only. P-05 builds no payment, purchase, or transfer path; any step that would move money is rejected as out of scope (P-07). This is a testable gate assertion, not a comment.
7. **Long-running work is asynchronous.** Plan execution stays synchronous only for short steps (P-02's known limitation); P-05 execution steps run as P-01 tasks with progress events, so a slow browser/API call cannot block the API or the planner. Cancellation is cooperative through the P-01 task engine.

## 3. Data model additions (one Alembic migration, additive)

`executions` (mission/plan/agent FKs, workflow name, status, mode at start, budget consumed) · `execution_steps` (execution FK, order, handler name, redacted request, result summary, status incl. `unverified`, task FK, verification verdict) · `artifacts` (execution/step FK, kind file/page/response, workspace-relative path or content hash, size, provenance) · `sandbox_policies` (owner-governed: workspace root, allowed hosts, allowed methods, limits — editable only by owner/governance, Article 0: agents cannot edit it) · `external_calls` (step FK, host, method, status, duration, bytes — the audit trail for every call that left the machine).

## 4. API additions (all under /api/v1, same envelope/auth)

`POST /executions` (from an approved plan + assigned agent) · `GET /executions`, `GET /executions/{id}` incl. steps + artifacts + verification · `POST /executions/{id}/cancel` · `GET /artifacts/{id}` (workspace-relative only) · `GET /sandbox/policies`, `PUT /sandbox/policies` (owner only) · `GET /executions/{id}/calls` (external-call audit). Capability grants stay on the existing P-04 endpoints — no duplicate grant path.

## 5. Test plan (gate will require)

Unit: payload validation per handler (path escape, host not allowlisted, method not allowed, oversize), sandbox policy enforcement, budget accounting, artifact hashing, verification pass/fail/unverified paths. Integration: the acceptance scenario end-to-end with fake transport AND with fixture files (mission → plan → approve → assign agent with granted capability → execute → verified result → explanation from decision records); a plan step naming an unheld capability is rejected at validation; an expired/revoked grant blocks mid-execution; simulation mode refuses external-effect steps; cancellation stops a long execution cleanly. Security: prompt-injection text inside a fetched page or API response cannot create tools, raise permissions, or alter sandbox policies (Article 0 test, carried into every later phase); fetched content is parsed as untrusted data and schema-rejected when malformed; sandbox-escape attempts (path traversal, symlink, SSRF to non-allowlisted host, redirect to non-allowlisted host) are denied and logged as `SandboxViolation` events. Regression: full P-01–P-04 suite (230 tests) must stay green.

## 6. Acceptance scenario (the P-05 gate demo)

Mission (owner, supervised mode): *"Fetch the pricing page of the shop we already verified in P-03, save the verified price list into the workspace, and report what changed."* → CIO plans steps (`exec.api_read` on the allowlisted host, `exec.file_write` into the workspace) → plan approved → steps execute as P-01 tasks by an agent holding `api_read` + `file_write` → Verifier confirms the fetched content against the declared expectation and the written file against its hash → CIO explains the outcome from decision records, including which steps were verified and what was refused. Plus the negative demos: the same mission aimed at a non-allowlisted host is refused before any call; a fetched page containing hidden instructions is quarantined as data; a plan for an agent without the grants never executes.
