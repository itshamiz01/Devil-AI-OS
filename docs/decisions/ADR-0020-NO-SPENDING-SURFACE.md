# ADR-0020: §26's spending prohibition is structural — no endpoint, permission or config key implies money can be spent

- **Decision ID:** ADR-0020
- **Status:** Implemented for P-03
- **Context:** §26 of the phase brief prohibits P-03 from making any commercial commitment: no purchasing a domain, subscription, dataset or advertisement; no placing an order; no registering a business; no signing a contract; no collecting or transferring funds. The system already has a permission model with 28 codes, a configuration surface with 54 settings, an HTTP API with 58 operations, and a task layer that executes handlers on the owner's behalf.
- **Problem:** A prohibition implemented only as a runtime check is one refactor away from not existing. If the system has a `purchase` endpoint that returns 403, or an `opportunities.spend` permission nobody holds, or a `research_budget_usd` setting that happens to default to zero, then the capability is present and merely disabled — and any of those can be re-enabled by a configuration change, a permission grant or a code path that forgets the check. §26 is a phase-level prohibition, not a supervision setting, so it must not be expressible as a toggle.
- **Options considered:** (a) implement the operations and gate them behind a permission nobody holds; (b) implement them behind a config flag defaulting to off; (c) check at runtime in each handler and raise; (d) make the capability absent from every surface — no endpoint, no permission code, no config key, no handler — and enforce the boundary in the governance layer that *does* exist.
- **Selected decision:** (d), with (c) retained as defence in depth. There is no endpoint, permission code, configuration key or task handler anywhere in the system by which money can be spent. `GovernanceGate` carries all thirteen `PROHIBITED_*` actions so that any *attempt* to express one — including in free text routed through `GOVERNANCE_VERB_PATTERNS` and `OBLIGATION_PATTERNS` — is refused with a specific reason from `PROHIBITION_REASONS`.
- **Reasons:** (a) and (b) both leave a live capability behind a switch, and a switch is exactly what §26 says must not exist; they also create the standing temptation to "just enable it for testing". (c) alone is necessary but not sufficient — it protects the paths someone thought to guard and says nothing about the paths nobody wrote. (d) inverts the burden: instead of every new code path having to remember the prohibition, the prohibition is the absence of anything to call. The governance layer still exists because a refusal with a *reason* is more useful to an owner than a 404, and because free-text intents need to be caught before they reach a planner.
- **Consequences:**
  - `GovernanceGate.authorize` has signature `(self, action, *, detail=None)`. **It accepts no autonomy level parameter at all**, so there is no privilege, tier or autonomy setting that could weaken the refusal. A test inspects the signature and asserts `autonomy_level` is not among `['action', 'detail', 'self']`.
  - The four P-03 permission codes are `opportunities.read`, `opportunities.research`, `opportunities.manage`, `opportunities.sources`. All four go to the owner; **SYSTEM holds none**, so no internal component can drive the pipeline except by acting as the owner. There is deliberately no spending permission, because there is no spending.
  - A test asserts that **no path or operation summary in the whole OpenAPI document** contains `purchase`, `buy`, `order`, `pay`, `checkout`, `invoice`, `subscribe`, `contract`, `campaign`, `advert` or `domain`. The assertion runs over `app.openapi()` — 53 paths, 58 operations — so it covers every router, including ones added later.
  - `BudgetCompatibility.budget_was_modified` is a literal `False` that Pydantic will refuse to set to anything else, and `available_capital` is copied read-only from the owner's `BudgetConstraint`. The module's own docstring states that it *reports* a shortfall and never repairs one. Tested end to end: capital 10 against an 800 startup cost yields `incompatible`, `shortfall == 790.00`, `budget_was_modified is False`, and the owner's constraint object unchanged — the opportunity is classified `INCOMPATIBLE_WITH_CONSTRAINTS`. The constraint wins.
  - Two of the thirteen prohibitions are not about money and are enforced identically: `PROHIBITED_SHARE_CREDENTIAL_TO_MODEL` and `PROHIBITED_EXECUTE_RETRIEVED_CODE`. Text fetched from a source is data; executing it would make every permitted host a remote code execution path. `RetrievedContent` refuses any `trust_domain` other than `external`, which is what makes that fencing enforceable at all.
  - `DistributionAssessment.reachable_without_paid_ads` and `DistributionChannel.feasible_without_ad_spend` exist as first-class fields precisely because a channel requiring ad spend is not merely expensive in this phase — it is unusable, and the assessment must say so.
  - `PROHIBITION_REASONS` gives every prohibited action its own explanation rather than a generic "not permitted", e.g. `purchase_domain` → *"purchasing a domain creates a financial obligation; §26 reserves all spend to the owner"*. An owner must be able to judge whether a rule is right.
  - The thirteen `PROHIBITED_CATEGORIES` in `risk.py` are a separate and complementary control: they stop the system from *analysing* opportunities whose subject matter is prohibited, before any acquisition stage runs. A prohibited candidate halts at `initial_screening` and moves to `blocked_by_compliance`, from which the only edge is `archived`.
  - **Adding any of these back is a decision that requires a new ADR**, not a configuration change.
