# ADR-0015: Intelligence engine boundaries — reasons and recommends, never executes

- **Decision ID:** ADR-0015
- **Status:** Implemented for P-02
- **Context:** P-02 requires a Master Intelligence Engine that interprets owner requests, plans work and recommends decisions. The owner's framing for the phase is explicit: *"Its intelligence should be flexible. Its authority must remain bounded."* P-01 already provides the authoritative control surface — `PermissionEngine`, the approval service, `TaskManager` with exactly three registered safe handlers (ADR-0011), and phase flags that reject `external_execution_enabled`, `financial_execution_enabled` and `cloud_ai_enabled` at configuration load.
- **Problem:** An engine that can reason about arbitrary business objectives is one refactor away from being able to act on them. The boundary between *reasoning* and *authority* had to be structural rather than conventional, so that no future module could inherit execution power by importing the engine.
- **Options considered:** (a) let the engine call handlers directly when it judges a step safe; (b) give the engine its own permission checks, parallel to P-01's; (c) make the engine a pure producer of plans and recommendations, with every execution path passing through `TaskManager.submit` and every authorization decision passing through the owner; (d) defer the engine until P-04 supplies autonomous agents.
- **Selected decision:** (c). `backend/app/intelligence/` contains no shell, browser, filesystem-write or financial operation. Verified: `grep -rE "subprocess|os\.system|eval\(|exec\(|shell=True" backend/app/` returns nothing across the whole backend, including the intelligence package. Dispatch happens only in `orchestrator.TaskDispatcher`, which builds a `TaskSubmitRequest` and calls `TaskManager.submit` — the same entry point an owner uses, subject to the same permission checks, the same approval gate and the same idempotency key. The three-way separation is enforced in code, not documentation: `DecisionEngine` has **no** method that returns `DecisionStatus.AUTHORIZED` except `record_authorization(..., authorized_by_owner=)`, which raises `UnauthorizedDecisionError` when that flag is false.
- **Reasons:** (a) makes safety a property of the model's judgement, which is exactly what §10.4 forbids — a high-confidence response does not grant authorization. (b) creates two permission systems that can disagree, and the disagreement would always resolve in favour of whichever is more permissive. (d) abandons the phase. (c) keeps intelligence and authority in separate modules with a single, auditable choke point.
- **Consequences:**
  - At the default autonomy level (`0_advisory`) an approved plan dispatches **nothing**. `POST /missions/{id}/approve` returns `dispatched: []` with a message saying so plainly. This is deliberate: approval authorizes, the autonomy level permits, and only together do they execute (§16).
  - Progress percentages are computed by `ProgressMonitor` from persisted task rows only. A step whose task row is missing is marked `BLOCKED`, never `COMPLETED`, so a mission cannot be reported successful on the strength of a model's narration (§11.4).
  - `CapabilityRegistry.register` refuses any handler outside `REAL_HANDLERS = {system.noop, system.echo, system.wait}`. The engine therefore cannot advertise a capability that has no working implementation (§11.2). Four capabilities (`analyze.text`, `plan.generate`, `compute.deterministic`, `evaluate.decision`) are marked in-process: they are resolved by deterministic code and never queued.
  - A plan that names an unregistered capability, exceeds `plan_max_steps`, contains a cycle, or whose risk exceeds the mission's stated constraints is **rejected**, not repaired. `Planner` never creates a task that no registered capability supports (§9.5).
  - Cloud inference routing is **implemented and unit-tested but inert in the running application**. `ModelRouter` and `InferencePolicy` accept `cloud_enabled=True` and `test_model_router.py` exercises that path, but `Settings.validate_phase_flags` rejects `cloud_ai_enabled=true` at startup, so no deployed configuration can reach it. Enabling cloud inference is an owner decision requiring a phase-flag change, not a code change. See ADR-0016 for the fallback rule that applies once it is enabled.
  - Autonomy levels 3 and 4 are declared in `AutonomyLevel` so the boundary is explicit and refused by code rather than merely absent. `AutonomyController` raises `AutonomyEscalationError` for them unconditionally, even with `authorized_by_owner=True`, and `Settings.autonomy_level` is a `Literal` that excludes them, so they cannot be set by configuration either (§15).
  - A model can never raise its own autonomy level. `request_change` requires `authorized_by_owner` and a non-empty `principal_id`; refusals are recorded in `history` rather than dropped, because a silently refused escalation is as misleading as a silently granted one.
  - **Requires owner ratification:** the inert-but-implemented cloud path is a deliberate asymmetry. The alternative — deleting the code — would make the local-first rule untestable; the alternative of enabling it would violate the phase flags. The owner should confirm this is the intended posture.
