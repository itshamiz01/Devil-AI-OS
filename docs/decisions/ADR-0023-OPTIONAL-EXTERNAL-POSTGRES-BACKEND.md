# ADR-0023: The database backend is selected by one optional configuration key, and SQLite stays the tested default

- **Decision ID:** ADR-0023
- **Status:** Implemented; **never executed against a real Postgres server** (see Consequences)
- **Context:** Until this decision the application was SQLite-only. `backend/alembic.ini` pointed at `sqlite:///../data/autonomus.db`; the migration chain rendered every ALTER through `render_as_batch=True`; `Database.__init__` registered a `PRAGMA foreign_keys=ON` listener unconditionally; `run_migrations_sync` created the data directory unconditionally; and `requirements.txt` contained no Postgres driver. A Supabase project now exists to hold the data, and the intended host for the API is Vercel, whose filesystem is ephemeral and largely read-only.
- **Problem:** SQLite cannot satisfy that deployment: a file written on one serverless invocation is gone by the next, and a read-only filesystem cannot create the data directory at all. Worse, the existing code did not merely fail to support Postgres — it **crashed** on it. `PRAGMA` is not valid PostgreSQL, so the connect listener would raise on every connection, and `mkdir` on the data directory would raise on a read-only filesystem. Supporting an external database therefore required changes in the configuration, the connection layer and the migration chain, not just a new dependency.
- **Options considered:** (a) stay SQLite-only and accept that the API cannot persist data when hosted serverlessly; (b) replace SQLite with Postgres as the only backend; (c) make an external URL optional, leaving SQLite as the default; (d) keep two separate configuration surfaces, one for local and one for cloud.
- **Selected decision:** (c). One key, `AUTONOMUS_DATABASE_URL`. Unset or empty means the local SQLite database exactly as before; set means both the async and the sync engine target that URL, with the driver normalised to `psycopg3`.
- **Reasons:** (b) would break the single-owner local design that every one of the 513 tests exercises, and would invalidate ADR-0014, whose backup and restore are a verified file copy of the SQLite database. (d) doubles the surface that has to be audited for no reason — the two URLs are the same value seen by two engines. (a) is simply untrue about the deployment. (c) keeps the tested default, makes the switch one environment variable, and — importantly — **fails loudly**: a `mysql://` or `sqlite://` URL is a construction error, not a silent fallback to SQLite. A silently ignored URL would leave the application writing locally while the operator believed it was writing to the cloud database, which is the worst available outcome.
- **Consequences:**
  - `psycopg[binary]==3.3.7` is the only new dependency. One driver serves both APIs, since psycopg3 supports synchronous and asynchronous use; `async_database_url` and `sync_database_url` are both rewritten to the `postgresql+psycopg://` scheme whatever scheme the operator supplied.
  - `pool_pre_ping` is enabled **only** for an external database. Transaction poolers close idle connections between requests, so a pooled connection may be dead on arrival; a local SQLite file needs no such check and would only pay for it.
  - The `PRAGMA` listener and the data-directory `mkdir` are both gated on `Settings.database_is_sqlite`. Neither runs against Postgres.
  - `render_as_batch` is now dialect-conditional in `env.py`, and the four revisions in the chain call `portable_alter_table` from `app/database/migrations/portable.py` instead of `op.batch_alter_table`. This matters more than it looks: batch mode rebuilds a table for every operation, so the chain's **144 index operations** would have produced 144 table rebuilds on Postgres. Through the shim they become plain `CREATE INDEX` / `DROP INDEX`, and the two NOT NULL `ADD COLUMN`s become plain `ALTER TABLE`. Verified by offline render of the full chain against a `postgresql+psycopg://` URL: **35 CREATE TABLE, 2 ALTER TABLE, 65 CREATE INDEX, and zero SQLite-isms** in the emitted SQL.
  - **The chain has never been executed against a real Postgres server.** Offline rendering proves what SQL is generated, not that a server accepts it. The first `alembic upgrade head` against the Supabase project is the real test, and it should be run against an empty database before any data exists.
  - Supabase exposes two connection strings. The **transaction pooler** (port 6543) is appropriate for the running application; the **direct connection** (port 5432) is appropriate for migrations, because a transaction-mode pooler breaks multi-statement DDL and prepared statements. Both should be kept, and only the runtime one should be wired to `AUTONOMUS_DATABASE_URL`.
  - Offline `alembic upgrade --sql` still cannot render the **SQLite** branch of the chain, because batch mode needs a live connection to reflect the table it rebuilds. This predates the decision and is unchanged; the SQLite path is always applied online by `run_migrations_sync`.
  - ADR-0014 (verified file-copy backup, CLI-only restore) is SQLite-only and has no equivalent for an external database in this codebase. ADR-0022 still holds: decimal columns are `String(32)` on both dialects, so the exact-text round trip does not depend on which backend is in use — at the cost of forgoing Postgres `NUMERIC`, which would be a cross-cutting change to the P-01/P-02/P-03 monetary model.
