# ADR-0019: A flat `app/opportunities/` package rather than the nested tree in §4

- **Decision ID:** ADR-0019
- **Status:** Implemented for P-03
- **Context:** §4 of the phase brief sketches the opportunity layer as a nested package tree — subpackages for discovery, research, analysis, scoring, validation and reporting. §2 names fourteen architecture documents, eight of which do not exist in this repository (`AUTONOMOUS_MASTER_CONSTITUTION.md`, `AUTONOMOUS_DEVELOPMENT_PROMPT_PACK.md`, `MASTER_INTELLIGENCE_ARCHITECTURE.md`, `MODEL_ROUTING_ARCHITECTURE.md`, `REASONING_PIPELINE.md`, `STRATEGIC_PLANNING_ENGINE.md`, `DECISION_INTELLIGENCE.md`, `MASTER_ORCHESTRATOR.md`); their actual equivalents are `INTELLIGENCE_ENGINE.md`, `MODEL_ROUTING.md`, `REASONING_AND_EVIDENCE.md`, `PLANNING_AND_DEPENDENCIES.md`, `DECISION_ENGINE.md` and `ORCHESTRATION_AND_DISPATCH.md`. P-02 established the precedent of one flat `app/intelligence/` package with 18 modules.
- **Problem:** Following §4 literally would mean six subpackages averaging under three modules each, with `__init__.py` files whose only job is re-export, and import paths that change whenever a module is judged to belong to a different concern. Following P-02's precedent departs from the brief's stated layout. Either choice needs recording, because a reader comparing the code to §4 will otherwise conclude the structure is accidental.
- **Options considered:** (a) implement §4's nested tree exactly; (b) a flat package matching P-02, with the mapping to §4 written down; (c) a hybrid — flat for the analytics, nested for sources and reports.
- **Selected decision:** (b). `backend/app/opportunities/` is flat: seventeen modules, one concern each, with `__init__.py` re-exporting **124 names** and carrying an eleven-row table mapping the flat modules to the subpackages §4 describes. The mapping was verified so that **zero of the 124 exports are unresolvable**.
- **Reasons:** (a) buys directory depth without buying separation — the modules already have single responsibilities, and the boundaries that matter (no analytics module touches persistence; no source module touches scoring) are enforced by what each module imports, not by which folder it sits in. (c) is the worst of both: two structural conventions in one package. (b) matches the phase that immediately precedes it, so a reader who has understood `app/intelligence/` needs no new mental model, and it keeps the audit tooling simple — `scripts/audit_p03_persistence.py` reasons about one `repository.py` rather than a tree of them.
- **Consequences:**
  - Where a name lives is not always where §4 implies, so the mapping is recorded in the package docstring. Concretely: `DiscoveryContext` and `DiscoveryReport` are in `discovery.py`; `WorkflowReport`, `StageResult`, `ResearchScheduler` and `ResearchTaskSpec` are in `research.py`; `HistoryEntry` is in `lifecycle.py`; `EventBus` is `app/events/bus.py`. `schemas.py` does **not** re-export the first three groups.
  - Everything a caller needs is reachable as `app.opportunities.<Name>`, so dependents do not encode module boundaries in their imports and a later restructuring is invisible to them.
  - The eight §2 documents that do not exist are recorded here rather than silently skipped, and the P-03 documentation set names the equivalents it relies on. Ten P-03 architecture documents were added under `docs/architecture/`, beginning with [`OPPORTUNITY_PIPELINE.md`](../architecture/OPPORTUNITY_PIPELINE.md).
  - Module sizes are deliberately kept comparable (190–2091 lines, `schemas.py` being the outlier because it holds every contract for the phase). No module was split to hit a line target, and none was merged to reduce a file count.
