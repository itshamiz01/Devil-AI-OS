# ADR-0013: Emergency stop foundation — durable state, owner-only, pause rather than cancel

- **Decision ID:** ADR-0013
- **Status:** Implemented for P-01
- **Context:** `SECURITY_FOUNDATION.md` §10 requires a global emergency stop that persists emergency mode, stops new external actions, revokes execution leases, cancels eligible work, **survives restart** and is **never cleared automatically**, while keeping essential audit, recovery and owner-control paths available. §11 assigns it to P-01 as a *foundation*, and separately assigns the restart-safe version with lease fencing and duplicate-effect prevention to **P-12**. Constitution §12 reserves emergency shutdown to the human owner.
- **Problem:** P-01 has no execution leases and no external actions, so §10 cannot be implemented literally. The control still has to be real, durable and owner-only — and it must not destroy recoverable owner work as a side effect of halting the system.
- **Options considered:** (a) in-memory flag only; (b) durable state plus hard-cancel of all in-flight work; (c) durable state, block new non-essential admission, cooperatively cancel RUNNING work and PAUSE queued work; (d) defer the whole control to P-12.
- **Selected decision:** (c). `core/emergency.py` persists state in the existing `system_configurations` table; `TaskManager` refuses non-essential admission while active; `apply_emergency_stop()` sets a cooperative cancellation request on RUNNING non-essential tasks and transitions QUEUED / RETRY_PENDING non-essential tasks to PAUSED. Essential handlers stay admissible. Clearing requires an explicit owner call to `POST /api/v1/system/emergency/clear` with a reason.
- **Reasons:** (a) fails the "survives restart" requirement outright. (d) leaves a documented P-01 security gate unmet. Between (b) and (c): every P-01 handler (`system.noop`, `system.echo`, `system.wait`) is side-effect free by ADR-0011, so cancelling queued work destroys recoverable owner state for zero safety gain, whereas PAUSED is a legal transition, is not auto-requeued, and is restored by an explicit owner resume. RUNNING work is cancelled *cooperatively* through the same mechanism `cancel()` uses, never hard-killed, satisfying P-01 §10.2.
- **Consequences:**
  - **Deliberate narrowing of §10, flagged for owner review:** queued non-essential work is **paused, not cancelled**. If the owner requires literal cancellation, this is a one-line change in `apply_emergency_stop()`, but it would make an emergency stop destructive of recoverable work.
  - Two event types beyond the P-01 §8 initial list — `EmergencyActivated`, `EmergencyDeactivated` — were added to `EVENT_TYPES`, because a security-critical state change must be observable and auditable through the same bus as everything else.
  - A new owner-only permission `system.emergency` was added. `OWNER_PERMISSIONS` is derived from the permission list, so the owner receives it automatically; `SYSTEM_PERMISSIONS` is enumerated explicitly and omits it, so the system principal can never halt or un-halt the application on its own authority.
  - Health reports `degraded` with `ready: true` during an emergency. Reporting not-ready would hide the very control path the owner needs in order to clear the halt.
  - The owner's free-text `reason` is persisted and returned to authorized callers but is **never written to log messages**, so it cannot be used to smuggle a secret past log redaction.
  - No execution leases, fencing tokens or external-action revocation are implemented; those remain P-12 obligations and are not claimed here.
