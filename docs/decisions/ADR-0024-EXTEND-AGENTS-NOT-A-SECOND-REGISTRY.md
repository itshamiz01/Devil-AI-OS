# ADR-0024: P-04 extends the existing `agents` table instead of creating a second agent registry

- **Decision ID:** ADR-0024
- **Status:** Implemented (P-04 Stage 2)
- **Context:** P-04 (Dynamic Agent Factory) requires a registry holding each agent's role, status, capabilities, configuration, history and health. An `agents` table already exists — 8 columns, `AgentRepo`, two read-only endpoints — and `tasks.assigned_agent_id` already references it. Its `status` default is the lowercase string `registered`, a value that appears in no lifecycle definition. A repository-wide search found **no code and no test that ever instantiates an `Agent`**: the table has never held a row in any run of this project's suite.
- **Problem:** A second table (say `agent_registry`) would give every agent two identities. Assignment, health and metrics would point at one while the existing FK and the shipped GET endpoints point at the other, and the two would drift — the same class of duplication the audit process already caught in P-03 (duplicated opportunity and source tables). Rebuilding `agents` instead would break `tasks.assigned_agent_id` and require a data copy through a migration that cannot be rendered offline on the SQLite branch.
- **Options considered:** (a) new `agent_registry` table, `agents` left as a legacy stub; (b) extend `agents` additively with the missing columns and add the new tables around it; (c) drop and recreate `agents` with the final shape, copying rows.
- **Selected decision:** (b). Additive columns only: `template_id`, `template_version`, `configuration_version`, `parent_agent_id`, `business_id`, `retired_at`, and a changed default plus CHECK on `status`. Nine new tables carry everything that did not exist: `agent_templates`, `agent_template_versions`, `agent_capabilities`, `agent_permissions`, `agent_assignments`, `agent_health`, `agent_metrics`, `agent_configuration_history`, `agent_creation_requests`. The database grows from 34 to 43 tables.
- **Reasons:** (a) duplicates identity for no capability gain and strands the existing FK. (c) is destructive on a column other tables reference and cannot be verified offline on SQLite, where batch mode needs a live reflection of the table being rebuilt. (b) keeps one agent identity, keeps `tasks.assigned_agent_id` meaningful, and is reversible: the downgrade drops the nine tables and the six columns and restores the previous default.
- **Consequences:**
  - **`status` now holds an uppercase lifecycle vocabulary** — `PROPOSED`, `PENDING_APPROVAL`, `INITIALIZING`, `ACTIVE`, `IDLE`, `BUSY`, `DEGRADED`, `SUSPENDED`, `FAILED`, `RETIRING`, `RETIRED` — while every other status column in the database stays lowercase (`tasks.status`, `approvals.status`, `missions.status`). That inconsistency is real and is recorded here rather than hidden: unifying it would mean rewriting the vocabulary of tables P-01 to P-03 already test against, which is out of scope for P-04. The CHECK constraint makes the agent vocabulary explicit at the column instead of implicit in service code.
  - **The legacy default `registered` is not a valid state, so the migration rewrites it.** The revision contains an explicit data step (`UPDATE agents SET status='ACTIVE' WHERE status NOT IN (…)`) placed before the CHECK is added. This is verified against a populated database in `tests/test_agents_schema_stage2.py`: an agent row written with `status='registered'` at the previous head comes out as `ACTIVE` after `upgrade head`. Had the CHECK been added without the rewrite, any deployment holding an agent row would fail the migration outright.
  - **Every constraint in this revision is named.** Alembic's autogenerate rendered an unnamed constraint as `op.drop_constraint(None, 'agents', type_='foreignkey')` in the downgrade, which cannot run. Naming the two new foreign keys (`fk_agents_template_id`, `fk_agents_parent_agent_id`) and all five CHECKs (`ck_agents_status_lifecycle`, `ck_agent_capabilities_approval_level`, `ck_agent_permissions_approval_level`, `ck_agent_assignments_delegation_depth`, `ck_agent_metrics_measurement_type`) makes both directions renderable.
  - **Autogenerate silently omits column-level `CheckConstraint`s from `create_table`** and omits CHECK additions and `server_default` changes on existing columns. All four new-table CHECKs and both `agents` status changes were added by hand to the revision and then proven by inserting invalid rows: an unknown lifecycle state, a fabricated `measurement_type`, `approval_level=7` and `delegation_depth=-1` are each rejected with an integrity error. Do not trust a generated revision to carry constraints.
  - `configuration_version` defaults to 1 and every change is intended to be written to `agent_configuration_history`, so the registry can answer "what configuration produced this behaviour" without reconstructing it.
  - `business_id` is a plain 36-character column, not a foreign key: there is no `businesses` table yet (P-06 is out of scope and must not be started), so the reference is documented rather than enforced.
  - `agent_metrics.measurement_type` is constrained to `measured`, `estimated`, `unavailable`, which is the schema-level half of the project rule that no number may be presented as a measurement unless something measured it.
  - The revision chain is now five revisions deep and still renders offline against `postgresql+psycopg://` with no SQLite-only statement; the portable shim gained `create_check_constraint`, `drop_constraint`, `alter_column` and `create_foreign_key` so the hand-written parts render on both dialects.
  - **Unchanged and still owed:** `agents.read` is absent from the authenticated `PERMISSIONS` list although it is present in `OWNER_PERMISSIONS`, so the two existing agent endpoints remain owner-only. P-04 Stage 3 resolves it; until then `agents.read` is not a capability any created agent can be granted.
