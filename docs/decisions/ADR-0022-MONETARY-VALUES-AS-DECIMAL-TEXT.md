# ADR-0022: Monetary and decimal values are stored as decimal text, and assessment summaries are stored independently of their child rows

- **Decision ID:** ADR-0022
- **Status:** Implemented for P-03
- **Context:** P-03 persists prices, cost amounts, contribution margins, shortfall figures, attractiveness scores and budget utilisation percentages. The database is SQLite via SQLAlchemy 2.1.6 with `render_as_batch=True`. SQLite has no decimal type: its storage classes are NULL, INTEGER, REAL, TEXT and BLOB. Twelve tables were added by revision `5953caf8f23e`, extended by `72ee9705e18f`.
- **Problem:** Two independent defects were found while building the persistence layer. First, storing a `Decimal` in a REAL column round-trips it through binary floating point, which changes the value by an amount no test comparing against a rounded literal would catch — a price of `19.99` and a margin of `0.20` both acquire representation error, and `Decimal` equality then fails against the value that was written. Second, storing only the child rows of an assessment loses the parent's verdict: a `RiskAssessment` with zero findings and one with `blocked=True` and zero findings are indistinguishable once only the findings are persisted, so "no risks were found" and "this opportunity is blocked" read back as the same state.
- **Options considered:** for decimals — (a) REAL columns; (b) INTEGER minor units (cents); (c) `Numeric` with a SQLAlchemy type decorator; (d) TEXT holding the decimal string. For summaries — (e) derive the parent from its children on read; (f) persist the parent summary as JSON on the opportunity row.
- **Selected decision:** (d) and (f). Every monetary and decimal column is `String(32)` holding the `Decimal`'s exact string form. `Opportunity` carries `business_model`, `distribution`, `competitor_assessment` and `risk_assessment` as JSON, written alongside — not instead of — their child rows.
- **Reasons:** (a) is the defect. (b) is exact for money but not for the non-monetary decimals in this phase — a contribution margin of `0.9000`, an attractiveness of `3.0000`, a utilisation percentage — which would each need their own scale, and a scale chosen wrong truncates silently. (c) works but ties correctness to a decorator being applied at every column and every query site; forgetting it once reintroduces (a) with no visible symptom. (d) is exact, needs no scale decision, round-trips `Decimal(str)` trivially, and is inspectable in the database file by eye — which matters for a system whose whole claim to trustworthiness is that its numbers can be traced. Its cost is that arithmetic cannot be done in SQL, and no P-03 query needs to: aggregation happens in Python over fully-loaded rows. (e) is the second defect — it cannot represent a parent verdict that is not a function of its children. (f) keeps the child rows queryable while making the verdict authoritative on read.
- **Consequences:**
  - Decimal columns are `String(32)`. A migration test asserts the round trip is **byte-identical**, so `19.99` read back is the same text that was written.
  - `OpportunityScore.attractiveness` is a `Decimal` quantised to **4 decimal places**. A zero score compares equal to `Decimal("0")` and *not* to the string `"0"` — a distinction that caught a defect in the test suite rather than in the code.
  - Assessment summaries are stored as JSON on the opportunity row, and `repository.py` **raises on an unknown parent** rather than defaulting, so a malformed summary cannot be silently read back as an empty assessment.
  - `assumptions` is the one JSON column in P-03 that holds Pydantic models. That combination does not serialise on its own — committing one raises `TypeError`, surfaced as a `StatementError`. Every read and write path goes through a shared `_assumptions()` / `_to_assumptions()` pair rather than relying on each call site to remember; five sites needed it.
  - `Opportunity.costs` and `Opportunity.validation` have `default_factory`, so an unanalysed opportunity carries an empty `CostStructure` and a level-0 `ValidationAssessment` rather than `None`. That is why report sections F and I can always render.
  - `OpportunityHistory.metadata_` maps to a column named `metadata`, because `metadata` is reserved on the SQLAlchemy declarative base.
  - `research_sources` has **no credential column**, and `SourceDescriptor` has no credential field. Credentials exist only as a constructor argument to `HttpSourceAdapter`, so they cannot be persisted, snapshotted or logged — there is nowhere in the data model to put them.
  - **Revision `72ee9705e18f` is a lesson recorded here because it nearly shipped broken.** It was autogenerated to add two NOT NULL JSON columns, and it failed on a *populated* database with `Cannot add a NOT NULL column with default value NULL`: `default=dict` is Python-side and never reaches DDL. An empty-database round trip passes regardless, so the defect was invisible to the test that existed. The revision was rewritten with `server_default=sa.text("'{}'")` and a `test_migration_is_safe_on_a_populated_database` test was added. **Any future migration adding a NOT NULL column must set `server_default` and must be tested against a populated database.**
  - Both P-03 revisions are additive and reversible, produce a byte-identical schema hash on a round trip, and enforce foreign keys. Neither was amended after being pushed; `9b65c3f69123` is a dead revision left in place rather than edited.
