# ADR-0012: Secret store is designed in P-01, implemented where a live secret first exists

- **Decision ID:** ADR-0012
- **Status:** Accepted for P-01 (design delivered; implementation deferred)
- **Context:** `SECURITY_FOUNDATION.md` §11 lists "secret-store design" among the P-01 minimum security gates. P-01 §13.10 requires "Protect local secrets". `keyring` 25.7.0 is recorded in `TECHNOLOGY_VALIDATION.md` as a *candidate only*, and `D-05` (toolchain approval) is still pending.
- **Problem:** P-01 holds no plaintext secret. Owner passwords are Argon2id hashes and session tokens are stored as SHA-256 hashes, so there is nothing for a live store to protect. Building one now would create a module with no consumer — the empty placeholder that P-01 §3 and Rule 3 forbid. Adding `keyring` would also extend the approved stack without authorization and could not be verified against Windows Credential Manager from this Linux workspace.
- **Options considered:** (a) implement a `keyring`-backed store in P-01; (b) implement an encrypted-file store with an application-held key; (c) deliver a design contract only, and implement in the phase that first holds a live external secret; (d) defer the whole topic silently.
- **Selected decision:** (c). `docs/architecture/SECRET_STORE_DESIGN.md` specifies the threat model, the `SecretStore` interface, backend selection, fail-closed behavior and the acceptance criteria the implementing phase must meet. No secret-store code and no new dependency are added in P-01.
- **Reasons:** Satisfies the gate as written ("design"). Avoids an unauthorized stack change under a pending `D-05`. Avoids a consumerless module. Option (b) was rejected on principle: if the application holds the encryption key, that key must itself be stored, which regresses to plaintext on the same disk. Option (d) was rejected because it would leave a documented P-01 gate unmet and unreported.
- **Consequences:** P-05 (browser sessions) and P-07 (wallet/payment credentials) inherit a fixed contract rather than inventing one under schedule pressure, and must satisfy the seven acceptance criteria in §7 of the design — including proving no secret value reaches a log file and that the store fails closed with no secure backend. `keyring` remains absent from `requirements.txt`; adding it requires an owner decision. Secrets live outside SQLite, so the P-01 backup/restore feature deliberately does not back them up, and losing the OS credential store is not recoverable from an application backup. Host-administrator tampering remains an unsolved residual limitation, consistent with `L-16`.
