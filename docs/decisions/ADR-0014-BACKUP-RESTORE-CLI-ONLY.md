# ADR-0014: Database backup and restore — online snapshot API, verified, CLI-only restore

- **Decision ID:** ADR-0014
- **Status:** Implemented for P-01
- **Context:** `SECURITY_FOUNDATION.md` §11 requires "migration/backup tests" of P-01, and §14 lists "backup restore" among the scenarios that must be tested. Constitution §10 requires backup and recovery. The database runs SQLite with `journal_mode=WAL`. Migrations were already exercised by the test suite; backup and restore did not exist at all, and neither did the `backups/` directory.
- **Problem:** Provide real, verifiable backup and recovery without creating a path by which a leaked session token — or a mistaken owner action — could destroy the audit trail.
- **Options considered:** (a) plain file copy of `autonomus.db`; (b) SQLite online backup API with post-hoc integrity verification, restore exposed over HTTP behind owner auth; (c) the same backup mechanism with restore restricted to the CLI; (d) defer backup entirely to a later phase.
- **Selected decision:** (c). `database/backup.py` snapshots through `sqlite3.Connection.backup`, verifies the *copy* with `PRAGMA integrity_check` plus a required-schema check, discards any snapshot that fails verification, and prunes to `AUTONOMUS_BACKUP_RETENTION_COUNT`. Backup is available programmatically; **restore is CLI-only** (`autonomus restore --from <path>`), requires typing `RESTORE`, preserves the displaced database as a `.pre-restore-<timestamp>` copy, and refuses to run while a live backend pid is detected.
- **Reasons:** (a) is incorrect under WAL — a file copy can miss committed transactions still resident in `-wal` and yield a torn snapshot that passes no integrity check anyone runs. (d) leaves a documented P-01 gate unmet. Between (b) and (c): P-01 §12 forbids exposing dangerous internal functions through HTTP endpoints and forbids leaving administrative operations publicly accessible. An HTTP restore is destructive and irreversible in effect, and gating it on a bearer token still places it one leaked session away from erasing the audit trail — the exact "audit evasion" threat `SECURITY_FOUNDATION.md:38` assigns to P-01. A local CLI invocation requires host access the attacker would already need.
- **Consequences:**
  - Restore requires host-level access, so an operator recovering a machine must use the CLI rather than the API. This is intentional friction, documented in `DATABASE_IMPLEMENTATION.md`.
  - A backup is never reported successful until the copy itself verifies; an unverifiable snapshot is deleted rather than left to be mistaken for a good one.
  - `restore_backup(assume_stopped=True)` exists because a `backend.pid` file can survive a hard process-group kill (a known P-01 issue). It bypasses only the liveness check — never integrity verification — and the CLI surfaces it as an explicit flag.
  - WAL/SHM sidecars are removed before a restore, so SQLite cannot replay obsolete frames over restored content.
  - **Tamper-resistance limitation, stated because P-01 §11 requires it:** backups are ordinary files on the same host as the database. They protect against accidental corruption and application-level mistakes. They are **not** cryptographically immutable and give no protection against a host administrator, who can alter or delete backups and the audit table alike. Owner-protected off-machine backups remain a later-phase concern.
  - Secrets are **not** covered: per ADR-0012 they will live outside SQLite, so no application backup contains them and losing the OS credential store is not recoverable this way.
  - Retention is bounded so backups cannot silently consume the disk that `monitoring.system_monitor` is watching.
