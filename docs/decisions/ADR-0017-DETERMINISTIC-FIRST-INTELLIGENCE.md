# ADR-0017: Deterministic-first intelligence; models are never the source of authority or evidence

- **Decision ID:** ADR-0017
- **Status:** Implemented for P-02
- **Context:** The P-02 host has no inference runtime, no GPU, 3.85 GiB of RAM and no swap, and neither `ollama.com` nor `huggingface.co` is reachable from it. Model weights cannot be downloaded and no local model can be run. The phase nonetheless has to deliver an engine whose behaviour can be tested.
- **Problem:** Two failure modes were available. The first is to stub a model and let fabricated output flow through the pipeline, which produces green tests that prove nothing about the real system. The second is to make the engine unusable without a model, which would leave the phase unverifiable on the hardware it was built on and would make every future test depend on a 2 GiB download.
- **Options considered:** (a) require a local model for P-02 to function; (b) mock models in production code paths so the engine always has something to call; (c) put every deterministic operation in code, use models only for genuinely semantic work, and report that work unavailable when no model is present; (d) ship a small bundled model.
- **Selected decision:** (c). Request categorisation, mission classification, constraint and budget extraction, clarification detection, risk assessment, task decomposition, dependency resolution, plan validation, decision scoring, autonomy enforcement, context assembly and state transitions are all implemented in code and run with zero models installed. Models are used only where semantics genuinely require them — enriching an interpretation, or analysing untrusted external text — and every such path returns an explicit `ModelUnavailableError`-derived limitation when no permitted model exists. Mock providers appear **only** in `backend/tests/`, per §19.1.
- **Reasons:** (a) and (d) are impossible on this host and would make the test suite unreproducible. (b) is the worse engineering choice: a mock in a production path is indistinguishable from a real model to the code around it, so the system would learn to trust fabricated output — precisely the failure §8.2 exists to prevent. (c) makes the deterministic core testable today and the semantic layer testable through injected mocks, with no path in which a fabricated answer can be mistaken for a real one.
- **Consequences:**
  - `ReasoningTrace.model_calls == 0` on the deterministic path, and a test asserts it. A plan generated with no model installed is a real plan, produced by real code.
  - **A model-generated statement is never verified evidence.** `Evidence._model_output_is_never_verified` makes `EvidenceReliability.MODEL_GENERATED` incompatible with `verification_status=VERIFIED` at construction, so the rule cannot be bypassed by a caller. `EvidenceManager.confirm` additionally refuses to let model output confirm model output, which would otherwise let the system bootstrap its own facts.
  - Confidence figures always carry `confidence_basis="unvalidated_estimate"`. `HypothesisRecord` defaults to the same value, so a persisted confidence can never be read back as a measured probability (§8.3).
  - `DEFAULT_WEIGHTS` is documented in code as *"a transparent ordering heuristic, not a probability model"*, and every `Decision.reasoning_summary` states that the score is not a probability of success (§10.2). A `DecisionScorer` validates its weight names against `DecisionOption.model_fields` at construction; a criterion whose name does not match a real field would otherwise be silently ignored by `getattr`, which is a defect this phase actually found and fixed.
  - `UncertaintyManager` refuses to conclude when evidence is insufficient or contradictory. `InsufficientEvidenceError` is the honest outcome, and the engine can say *"I do not have enough information"* (§8.4).
  - Structured model output is never trusted. `StructuredOutputParser` validates against a Pydantic schema with `extra="forbid"`, allows exactly one repair attempt at `temperature=0.0`, and refuses any payload containing an authority-bearing field (`budget`, `authorized`, `approved`, `permission`, `autonomy_level`, `risk_override`, `success_criteria`, `credentials`, `secret`, and variants) at any nesting depth (§13, §16).
  - Where a model *is* available, `_enrich_with_model` may set only non-authoritative fields — objective, intended outcome, deliverables, assumptions, missing information, and required capabilities intersected with the real registry. It may never set a constraint, a financial limit, a risk level or an approval requirement (§7.4).
  - **Local-model integration is NOT VERIFIED.** No measurement of latency, memory or token throughput was taken, because no model could be run. No such figure appears anywhere in the P-02 documentation, and none may be inferred from these tests (§25: do not invent performance measurements). `OllamaProvider` is implemented against the documented HTTP API and is exercised only through mocks; whether it works against a real server is untested and labelled accordingly.
